圃場非表示化機能 実装手順書

ステータス: 未着手

測定データが紐づく圃場は物理削除できない現行仕様を維持しつつ、ユーザからは「削除」と同等の体験で 圃場一覧・各種画面から見えなくする（非表示化＝ソフトアーカイブ）機能を追加する。 測定データそのものは会社資産として保持し続け、物理削除は行わない。

目次
  • 0. 実装方針サマリ
  • 1. Laravel側（バックエンド）
  • 2. Flutter側（モバイルアプリ）
  • 3. 影響範囲チェックリスト
  • 4. リリース・ロールバック手順

0. 実装方針サマリ

項目内容
DB変更 farms テーブルに hidden_at（nullable timestamp）を追加。既存カラム・既存リレーションは変更しない（非破壊的追加）。
app_user_id の扱い 変更しない。所有者情報として維持し、非表示状態の管理には使わない。
API変更 DELETE /api/v1/farms/{farm} の内部ロジックを分岐：測定データがなければ従来通り物理削除、あれば hidden_at を設定して非表示化（200を返す）。
一覧系APIの変更 モバイル向け一覧・結果閲覧系APIすべてに hidden_at IS NULL のフィルタを追加。
Web管理画面 フィルタは適用しない（非表示化された圃場も引き続き閲覧可能。将来的に復元ボタンを追加）。
Flutter側の変更 API仕様（エンドポイント・パス）は変更しないため通信層の改修は不要。削除ボタンの確認ダイアログ文言、422分岐処理の見直しが中心。

Laravel1. バックエンド実装手順

1-1. マイグレーション追加

1

対象: database/migrations/xxxx_add_hidden_at_to_farms_table.php

新規マイグレーションファイルを作成し、farms テーブルに hidden_at カラムを追加する。既存カラムには一切触れない。

Schema::table('farms', function (Blueprint $table) {
    $table->timestamp('hidden_at')->nullable()->after('boundary_polygon');
});

down() では単純にカラムを削除する。

Schema::table('farms', function (Blueprint $table) {
    $table->dropColumn('hidden_at');
});
2

実行

php artisan make:migration add_hidden_at_to_farms_table --table=farms
php artisan migrate

ステージング環境のRDSに対して先に適用し、既存クエリに影響が出ないことを確認してから本番適用する。

1-2. Farmモデルの修正

3

対象: app/Models/Farm.php

hidden_at を $casts に datetime として追加し、モバイル向けクエリで使う専用スコープを定義する。

protected $casts = [
    'boundary_polygon' => 'array',
    'hidden_at' => 'datetime',
];

// ユーザに見える圃場のみ
public function scopeVisible($query)
{
    return $query->whereNull('hidden_at');
}

// 測定データ（uploads）が1件でも存在するか
public function hasMeasurementData(): bool
{
    return $this->uploads()->exists();
}

public function hide(): void
{
    $this->update(['hidden_at' => now()]);
}

public function unhide(): void
{
    $this->update(['hidden_at' => null]);
}

※ uploads() リレーションが未定義の場合は合わせて定義する（hasMany(Upload::class)）。

1-3. 圃場削除エンドポイントの分岐処理

4

対象: 圃場削除を処理しているコントローラ（例: app/Http/Controllers/Api/FarmController.php の destroy()）

現行の「測定データがあれば422」というロジックを、以下のように分岐させる。

public function destroy(Farm $farm)
{
    $this->authorizeOwner($farm); // 既存の本人確認処理

    if ($farm->hasMeasurementData()) {
        $farm->hide();
        return response()->json([
            'message' => 'farm_hidden',
            'farm_id' => $farm->id,
        ], 200);
    }

    $farm->delete();
    return response()->json(['message' => 'farm_deleted'], 200);
}
既存仕様では測定データがある圃場の削除は 422 を返して拒否していた。今回の変更により 422は返らなくなり、常に200が返るため、Flutter側で422を専用エラーとして処理している箇所は 挙動確認・修正が必須（詳細は2章）。

1-4. 一覧・結果閲覧系APIへのフィルタ適用

5

以下のモバイル向けエンドポイントのクエリに ->visible() を追加する。管理画面（Web）側のクエリには追加しない。

エンドポイント用途対応
GET /api/v1/farms圃場一覧（圃場管理タブ）Farm::visible()->where('app_user_id', ...)
GET /api/farms/with-latest-result結果閲覧タブの圃場ごと最新結果クエリ起点に visible() を追加
GET /api/results/latest直近3件の最新結果join元の farms に hidden_at IS NULL 条件を追加
GET /api/farms/{farmId}/results/dates指定圃場の計測日一覧非表示圃場への直接アクセス時は404を返す（下記参照）
GET /api/farms/{farmId}/results/map指定日の地図データ同上
測定フロー Step3 圃場選択API本測定前の圃場選択一覧visible() を追加
6

対象: 個別圃場を farm_id で直接引く系のエンドポイント（results/dates、results/map など）

URLを直接叩かれた場合（キャッシュ・ディープリンク経由等）に非表示圃場のデータが見えてしまわないよう、 Route Model Binding後に所有者チェックと同じタイミングで非表示チェックを入れる。

if ($farm->hidden_at !== null) {
    abort(404);
}

1-5. Web管理画面（任意・推奨）

7

対象: /farm-management 画面

非表示状態を示すバッジ（例: 「非表示中」）と、unhide() を呼び出す復元ボタンを追加する。 管理画面のクエリには visible() を適用せず、全件表示のままとする。

優先度は低いため、初期リリースでは「一覧に非表示バッジを出すだけ」でも可。復元ボタンは第2フェーズでも良い。

1-6. テスト観点

  • 測定データがある圃場を削除APIで叩く → hidden_at がセットされ、レコードは残る（物理削除されない）
  • 測定データがない圃場を削除APIで叩く → 従来通り物理削除される
  • 非表示化後、GET /api/v1/farms 等の一覧系APIに出てこない
  • 非表示化した圃場の results/dates 等に直接アクセスすると404になる
  • Web管理画面では非表示化後も一覧・詳細から参照できる
  • 他ユーザの圃場に対して削除・非表示化APIが実行できないこと（既存の本人確認ロジックが維持されていること）

c. Feature Test の追加・実行

5

対象: tests/Feature/FarmDeleteTest.php（新規作成）

最低限、以下のケースをPHPUnit（Feature Test）として自動化する。

public function test_farm_with_measurement_data_is_hidden_not_deleted(): void
{
    $farm = Farm::factory()->has(Upload::factory())->create();

    $this->actingAsAppUser($farm->appUser)
        ->deleteJson("/api/v1/farms/{$farm->id}")
        ->assertOk()
        ->assertJson(['message' => 'farm_hidden']);

    $this->assertDatabaseHas('farms', ['id' => $farm->id]);
    $this->assertNotNull($farm->fresh()->hidden_at);
}

public function test_farm_without_measurement_data_is_hard_deleted(): void
{
    $farm = Farm::factory()->create();

    $this->actingAsAppUser($farm->appUser)
        ->deleteJson("/api/v1/farms/{$farm->id}")
        ->assertOk()
        ->assertJson(['message' => 'farm_deleted']);

    $this->assertDatabaseMissing('farms', ['id' => $farm->id]);
}

public function test_hidden_farm_is_excluded_from_farm_list(): void
{
    $farm = Farm::factory()->create(['hidden_at' => now()]);

    $this->actingAsAppUser($farm->appUser)
        ->getJson('/api/v1/farms')
        ->assertOk()
        ->assertJsonMissing(['id' => $farm->id]);
}

実行

docker compose exec app php artisan test --filter=FarmDeleteTest

Flutter2. モバイルアプリ実装手順

APIのエンドポイント・パスは変更しないため、通信層（dioクライアント）自体の改修は不要。 主な対応は「削除操作の文言・確認ダイアログの見直し」と「レスポンスハンドリングの見直し」。

2-1. 削除確認ダイアログの文言変更

1

対象: lib/features/farms/presentation/ 配下、圃場削除の確認ダイアログ

「削除すると測定データも失われます」という趣旨の文言が現状ある場合、以下のように変更する。 バックエンド側で実際に物理削除されるか非表示化されるかはユーザに区別させる必要はないため、 文言は共通で構わない。

この圃場を一覧から削除しますか？
※ 測定データがある場合、圃場は一覧から非表示になります
　 （データ自体は保持されます）

2-2. 削除処理のレスポンスハンドリング見直し

2

対象: 圃場削除APIを呼び出しているリポジトリ／サービスクラス（例: lib/features/farms/data/farm_repository.dart）

現状 422 を「削除不可（測定データあり）」として専用エラーハンドリングしている箇所があれば、 その分岐は基本的に到達しなくなる（サーバ側が200を返すようになるため）。ただし後方互換のため 422ハンドリング自体はコードに残しておき、想定外エラーとしてログに残す形にしておくのが安全。

try {
  final res = await _dio.delete('/api/v1/farms/$farmId');
  // res.data['message'] は 'farm_deleted' or 'farm_hidden'
  return FarmDeleteResult.success;
} on DioException catch (e) {
  if (e.response?.statusCode == 422) {
    // 想定外経路。ログのみ残し、ユーザには汎用エラーを表示
    _logger.w('unexpected 422 on farm delete: ${e.response?.data}');
  }
  return FarmDeleteResult.failure;
}

2-3. 圃場一覧の再取得タイミング確認

3

対象: lib/features/farms/presentation/providers/ の一覧系Notifier

非表示化はサーバ側でフィルタされるため、削除操作後に一覧APIを再取得（fetchFarms() 等）すれば 自動的に画面から消える。ローカルにキャッシュを保持している場合は、削除成功時に該当 farm_id を ローカルリストからも即時除去し、体感速度を落とさないようにする。

2-4. 測定フロー（圃場選択）・結果閲覧タブへの波及確認

4

以下の画面は同じ一覧系APIまたは同種のAPIを参照しているため、Laravel側の visible() 対応が 入れば自動的に非表示圃場が除外される。Flutter側での追加改修は基本不要だが、疎通確認は行うこと。

  • 測定タブ Step3「圃場選択」画面
  • 結果閲覧タブ「最新結果」「圃場ごとの結果一覧」
  • 圃場管理タブの圃場一覧

2-5. オフラインキュー（未アップロードデータ）との整合性

5

対象: PendingUploadStore

非表示化した圃場に対する未アップロードデータ（pending_uploads.json）が端末内に残っている場合、 アップロード自体はサーバ側で拒否していない（farm_id は生きたレコードのまま）ため技術的には アップロード可能。ただしユーザ体験としては「非表示にしたはずの圃場にデータが積み上がる」状態になり得るため、 未アップロード一覧画面で対象圃場が非表示化されている場合は、警告表示を出す対応を検討する （必須ではないため、初期リリースでは対象外としても良い）。

2-6. テスト観点

  • 測定データありの圃場を削除操作 → 一覧から消える／エラー表示が出ないこと
  • 測定データなしの圃場を削除操作 → 従来通り一覧から消えること
  • 削除後、測定タブの圃場選択に対象圃場が出てこないこと
  • 削除後、結果閲覧タブに対象圃場の過去結果が出てこないこと
  • オフライン時に削除操作をした場合の挙動（オフライン検知〜リトライ動線）が既存仕様と矛盾しないこと

4. リリース・ロールバック手順

1

デプロイ順序：Laravel側（マイグレーション＋API）を先にリリースし、Flutter側は後追いでリリースする。 Laravel側が先行しても、既存のFlutterクライアント（旧バージョン）は従来通り「200 or 422」のいずれかを受け取るだけで、 422時のエラーハンドリングは残っているため後方互換性は保たれる。

2

ロールバック：問題発生時は DELETE エンドポイントの分岐処理のみを旧ロジック（測定データありなら常に422）に戻せば、 マイグレーション（hidden_at カラム）はそのまま残しておいて問題ない。カラムを追加しただけの状態は 既存機能に影響しないため、DBロールバックは基本不要。
